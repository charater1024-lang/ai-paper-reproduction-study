# 01. 한국어 텍스트 전처리

이 실습에서는 고객 문의 원문을 **재현 가능한 규칙**으로 정리하고, 이메일·전화번호·주문번호처럼
모델 학습이나 로그에 남기면 곤란한 값을 토큰으로 치환합니다. 목표는 원문을 무조건 많이 지우는
것이 아닙니다. 의미에 도움이 되는 한국어·영어·숫자는 남기되, 같은 표현은 같은 형태로 만들고
민감한 값만 안전하게 가리는 작은 전처리 파이프라인을 이해하는 것이 핵심입니다.

API 키나 외부 형태소 분석기는 필요하지 않습니다. Python 표준 라이브러리만으로 원리를 먼저
익힌 뒤, 다음 분류·검색·RAG 프로젝트에서 왜 입력 품질이 중요한지 연결해 볼 수 있습니다.

## 학습 목표

실습을 마치면 다음을 할 수 있습니다.

- Unicode NFKC 정규화, 소문자화, 공백 정리가 각각 어떤 변형을 줄이는지 설명한다.
- 이메일, 한국 전화번호, 긴 주문 식별자를 원문 값 대신 `<EMAIL>`, `<PHONE>`,
  `<ORDER_ID>`로 치환한다.
- 한국어·영어·숫자·마스크 토큰을 원래 순서대로 추출한다.
- 여러 문서의 토큰 빈도를 `Counter`로 집계하고, 동률까지 재현 가능한 순서로 출력한다.
- 마스킹이 개인정보를 지우면서도 “이메일 문의”, “전화 문의”라는 유용한 범주 정보는
  보존하는 이유를 이해한다.

## 핵심 개념과 필요한 이유

### 1. 정규화는 겉모양만 다른 같은 문자를 합친다

컴퓨터에서 눈에 비슷하게 보이는 문자가 항상 같은 코드값은 아닙니다. 예를 들어 전각 영문
`Ｈｅｌｌｏ`, 일반 영문 `Hello`, 탭·줄바꿈이 섞인 문장은 그대로 세면 서로 다른 특징이 될 수
있습니다. `normalize_text`는 다음 세 단계를 적용합니다.

1. `unicodedata.normalize("NFKC", text)`로 호환 문자를 일반적인 형태로 바꾼다.
2. `lower()`로 영문 대소문자 차이를 없앤다.
3. 문자열을 공백 기준으로 나눴다가 한 칸으로 다시 합쳐 앞뒤 공백과 연속 공백을 없앤다.

예를 들어 `"  Ｈｅｌｌｏ\t한국어　ＮＬＰ\n①  "`는
`"hello 한국어 nlp 1"`이 됩니다. NFKC는 데이터 중복을 줄이는 데 유용하지만, 원문의
표기 자체가 중요한 과제에서는 정보 손실 여부를 먼저 검토해야 합니다.

### 2. PII 마스킹은 값은 숨기고 종류는 남긴다

개별 이메일 주소를 모두 서로 다른 토큰으로 학습시키면 어휘가 불필요하게 커지고 개인정보도
노출됩니다. 값을 통째로 삭제하면 “사용자가 연락처를 제공했다”는 정보까지 사라집니다. 따라서
이 실습의 `mask_pii`는 다음처럼 **값을 범주 토큰으로 바꿉니다**.

| 원문 예 | 결과 | 남는 정보 |
|---|---|---|
| `Student@example.com` | `<EMAIL>` | 이메일이 있었다 |
| `010-1234-5678` | `<PHONE>` | 전화번호가 있었다 |
| `주문번호: ORD-2026-12345678` | `주문번호: <ORDER_ID>` | 주문번호 문맥은 유지된다 |
| `20260814000123` | `<ORDER_ID>` | 긴 숫자 식별자가 있었다 |

처리 순서도 중요합니다. 전화번호를 긴 숫자 식별자보다 먼저 마스킹해야 하이픈이 없는
`01098765432`가 주문번호로 잘못 분류되지 않습니다. 이 예제의 규칙은 흔한 형식을 다루는
교육용 기준선입니다. 실제 서비스에서는 국가별 번호, 사내 식별자, 주소·이름 등 데이터 계약에
맞춘 규칙과 별도 보안 검토가 필요합니다.

### 3. 토큰화는 모델이 셀 단위를 정한다

`tokenize`는 정규표현식으로 다음 네 종류를 왼쪽에서 오른쪽 순서대로 추출합니다.

- 알려진 마스크: `<EMAIL>`, `<PHONE>`, `<ORDER_ID>`
- 한글 음절·자모
- 영문자
- 숫자

문장부호는 버리고, 붙어 있는 서로 다른 문자 체계는 나눕니다. 예를 들어
`한국NLP4 실습, <email> + RAG_2026!`은 대략
`["한국", "nlp", "4", "실습", "<EMAIL>", "rag", "2026"]`이 됩니다.
마스크 패턴을 일반 영문 패턴보다 먼저 검사해야 `<email>`이 `email`로 쪼개지지 않습니다.

이 방식은 쉽고 빠르지만 한국어 형태소를 분리하지 않습니다. 그래서 `해지와`, `해지하고`,
`해지`는 서로 다른 토큰입니다. 이 한계 자체가 뒤의 실험 과제가 됩니다.

### 4. 빈도 집계는 간단하지만 재현 가능해야 한다

`Counter.update(tokens)`를 사용하면 문서별 토큰을 누적할 수 있습니다. 빈도순으로 보여 줄 때는
빈도 내림차순만 사용하지 말고, 같은 빈도라면 토큰 사전순으로 정렬해야 실행할 때마다 결과가
안정적입니다. 참고 구현의 `top_terms`는 정렬 키 `(-count, token)`에 해당하는 규칙을 사용합니다.

## 데이터와 코드 흐름

기본 데이터는 프로젝트 루트의 `data/customer_support_tickets.csv`입니다. 100개 행의 고객지원
티켓이 있고, 이 실습에서는 그중 `text` 열만 읽습니다.

```text
CSV의 text 열
    ↓ load_ticket_texts
문장 목록 list[str]
    ↓ mask_pii
민감한 값 → 범주 마스크
    ↓ normalize_text
NFKC + 소문자 + 공백 한 칸
    ↓ tokenize
한국어/영어/숫자/마스크 토큰
    ↓ corpus_term_frequencies
말뭉치 전체 빈도
    ↓ top_terms
빈도 내림차순, 동률은 토큰 사전순
```

폴더의 파일 역할은 다음과 같습니다.

- `starter.py`: `prepare_text`, `count_terms`를 직접 구현하는 연습 파일
- `solution.py`: `llm_engineering_lab.nlp_basics`의 완성 함수들을 조합한 실행 예제
- `src/llm_engineering_lab/nlp_basics.py`: 재사용 가능한 실제 함수와 입력 검증이 들어 있는 모듈

starter와 solution은 이제 `PreprocessingConfig` → `PreprocessingReport` →
`TextPreprocessingProject`라는 같은 외곽 구조를 사용합니다. starter에서는
`prepare_text`와 `count_terms`의 핵심 규칙까지 직접 작성하고, solution에서는 검증된 공용
함수를 조합합니다. 따라서 정답을 비교할 때 함수 한 줄뿐 아니라 프로젝트 경계도 1:1로
대조할 수 있습니다.

문서 집합을 \(D\), 토큰을 \(t\)라고 하면 빈도 집계의 핵심은 다음과 같습니다.

$$
\operatorname{count}(t)=\sum_{d \in D}\sum_{u \in \operatorname{tokens}(d)}
\mathbf{1}[u=t]
$$

코드에서는 안쪽 합을 `Counter.update(prepare_text(document))`로 구현합니다. 이 수식을
별도 `count_terms` 함수로 둔 이유는 정규화·마스킹 규칙과 말뭉치 집계를 각각 테스트하기
위해서입니다.

## starter와 `solution.py` 1:1 코드 지도

| 단계 | starter/solution 코드 | 입력 → 출력 | 이 경계를 둔 이유 |
|---|---|---|---|
| 실험 설정 | `PreprocessingConfig` | 경로·상위 N → 불변 설정 | 실행 조건을 포트폴리오 결과와 함께 기록한다 |
| 데이터 계약 | `load_documents()` | CSV `(100, 8)` → `list[str]` 100개 | `text` 열 누락과 빈 데이터는 변환 전에 실패시킨다 |
| 단일 문서 변환 | `preprocess_one()` | `str` → masked·normalized·tokens | 세 중간값을 노출해 어느 규칙에서 값이 바뀌었는지 찾는다 |
| 집계 | `build_report()` | 문서 시퀀스 → `PreprocessingReport` | 출력용 문자열 대신 구조화 증거를 반환해 테스트·저장이 쉽다 |
| 불변 조건 | `validate_report()` | report → 성공 또는 예외 | 원본 이메일·전화번호가 남는 회귀를 즉시 중단한다 |
| 표현 | `print_report()` | report → 터미널 | 계산과 출력 책임을 분리한다 |
| 전체 실행 | `run()` | config → report | 같은 단계 순서로 재현한다 |

solution의 `preprocess_one()`은 **마스킹 → 정규화 → 토큰화** 순서를 명시합니다. 전화번호를
정규화 과정에서 먼저 훼손하거나, 이메일을 토큰화한 뒤 마스킹하면 원문 조각이 특징으로 남을
수 있기 때문입니다. `build_report()`는 `corpus_term_frequencies(...,
mask_sensitive_data=True)`와 `top_terms()`를 조합하며 동률은 토큰 사전순으로 고정합니다.

`parse_args()`의 `--data`, `--limit`는 `PreprocessingConfig`로 변환됩니다.
`ROOT = Path(__file__).resolve().parents[3]`를 쓰므로 Windows PowerShell의 현재 폴더와
무관하게 데이터와 `src`를 찾습니다. starter의 TODO를 구현하기 전에는 예외 대신
`연습 대기: ...`가 출력되며, TODO를 완성하면 solution과 같은 단계가 끝까지 실행됩니다.

## 예상 출력과 해석

기본 데이터에서 `--limit 15`로 실행하면 핵심 부분은 다음과 같습니다.

```text
[원문] ... 연락처 Student@example.com / 010-1234-5678
[마스킹] ... 연락처 <EMAIL> / <PHONE>
[정규화] ... 연락처 <email> / <phone>
[토큰] [..., '연락처', '<EMAIL>', '<PHONE>']

문서 수: 100
상위 토큰:
  무엇을               50
  방법을               50
  빠르게               50
  알려주세요             50
  처리하려면             50
  하나요               50
  해결                50
  해야                50
  확인하고              50
  관련                40
  문의입니다             32
  싶어요               22
  로그인               16
  배송                16
  갱신                12
```

`무엇을`, `빠르게`, `확인하고` 같은 일반적인 고객지원 문구가 가장 자주 등장합니다. 빈도가
높다고 해서 분류에 가장 유용한 단어라는 뜻은 아닙니다. 모든 의도에서 공통으로 등장하면
구분력은 낮을 수 있습니다. 반면 `로그인`, `배송`, `갱신`은 빈도는 더 낮아도 특정 의도와
연결될 가능성이 큽니다. 이 차이가 다음 프로젝트의 TF-IDF가 단순 빈도보다 유용한 이유입니다.

상위 빈도에서 `해지`, `해지와`, `해지하고`가 합쳐지지 않는다면 오류가 아니라 현재 단순
토큰화 방식의 한계입니다. 형태소 분석기를 적용했을 때 무엇이 달라지는지 실험할 수 있습니다.

## 실험 과제

한 번에 한 조건만 바꾸고, 변경 전후의 출력과 가설을 기록하세요.

1. **NFKC 효과 확인**: 전각 영문, 원문 영문, 원문 숫자와 동그라미 숫자 `①`를 섞은 문장을
   넣고 정규화 전후 토큰 수를 비교하세요.
2. **마스킹 경계 테스트**: 국내·국제 전화번호, 하이픈 없는 번호, 짧은 숫자, 레이블 없는 긴
   숫자를 모아 false positive와 false negative 표를 만드세요.
3. **불용어 실험**: `무엇을`, `빠르게`, `알려주세요` 등을 집계 단계에서 제외하고 상위 토큰이
   어떻게 바뀌는지 확인하세요. 원문 토큰화 결과는 유지하고 집계 단계에서만 제외해 보세요.
4. **토큰화 확장**: 한국어 조사나 어미를 단순 규칙으로 제거하거나 형태소 분석기를 적용해
   `해지와`·`해지하고`가 얼마나 합쳐지는지 비교하세요. 과도한 제거 사례도 기록하세요.
5. **n-gram 만들기**: `token_ngrams(tokens, 2)`를 사용해 unigram과 bigram의 상위 빈도를
   비교하세요. `로그인 실패`, `구독 해지`처럼 단어 하나보다 의미가 선명해지는 구가 있는지
   찾으세요.
6. **PII 회귀 테스트**: 가려야 할 예 10개와 남겨야 할 예 10개를 직접 만들고 `pytest`의
   parameterize 형태로 자동 검사하세요.

## 자주 생기는 오류와 디버깅

### `NotImplementedError`가 바로 발생한다

starter의 TODO가 아직 남아 있다는 뜻입니다. `prepare_text`를 먼저 완성해 sample 출력을
확인한 뒤 `count_terms`로 넘어가세요.

### 한글이 깨지거나 `UnicodeDecodeError`가 발생한다

CSV를 열 때 `encoding="utf-8"`을 사용했는지 확인하세요. Windows 기본 인코딩에 맡기지 않는
것이 좋습니다. 터미널 표시만 깨지고 값 자체는 정상인지 `repr(text)`로도 확인할 수 있습니다.

### 이메일이 `student`, `example`, `com`으로 남는다

토큰화 전에 마스킹하지 않았거나 이메일 정규표현식이 너무 좁은 경우입니다. 파이프라인 각 단계의
중간 문자열을 출력하고, `+`, 점, 대문자가 포함된 이메일을 별도로 시험하세요.

### `<EMAIL>`이 `email`로만 추출된다

토큰 정규표현식에서 일반 영문 패턴이 마스크보다 먼저 매치되거나 꺾쇠를 포함한 마스크 패턴이
없는 경우입니다. alternation의 마스크 경우와 대소문자 표준화 로직을 점검하세요.

### 전화번호가 `<ORDER_ID>`로 바뀐다

긴 숫자 패턴을 전화번호 패턴보다 먼저 적용했을 가능성이 큽니다. 치환 순서를 바꾸고 하이픈 없는
휴대전화 번호를 회귀 테스트로 추가하세요.

### 짧은 숫자까지 모두 사라진다

주문번호 정규표현식의 최소 길이와 단어 경계가 너무 넓습니다. `2026`, `500`, `4`처럼 남아야
하는 반례를 추가한 뒤 패턴을 좁히세요.

### 빈도 동률 순서가 예상과 다르다

`Counter.most_common()`의 동률은 처음 발견된 순서의 영향을 받습니다. 완전히 재현 가능한
표시가 필요하면 `(빈도 내림차순, 토큰 오름차순)` 기준으로 명시적으로 정렬하세요.

### `TypeError: corpus must be an iterable of document strings`

문장 목록 대신 문장 하나를 `corpus_term_frequencies`에 직접 전달했는지 확인하세요. 문장 하나도
`[text]`처럼 리스트로 감싸야 문자 하나씩 문서로 오해하지 않습니다.
